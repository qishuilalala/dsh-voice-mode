## 0. 一句话结论

**打断链的语义已经收敛（最难的部分过去了），但整个实时环路跑在一条请求-响应传输上，并且所有声学参数没有回归基准——前者是延迟与复杂度的结构性上限，后者是"下一次改动把自打断改回来"的必然风险。下一步的最高 ROI 不是加功能，而是把 VAD 下沉到浏览器 + 建立离线声学基准。**

## 2. 当前的「失」

### 2.1 架构师视角

#### A1【根因级】实时环路跑在请求-响应传输上

**现象**：一个必须逐帧判定的实时环路（采集 → 打断判定 → 停播），被实现为 100ms 节拍的 HTTP POST 轮询。

**证据**：
- `asr.ts:115` `PARTIAL_INTERVAL_MS = 100`；`asr.ts:700-707` 每拍二选一发 `requestPartial()` 或 `requestDetect()`
- 每包裹挟 f32 PCM（`asr.ts:375` `body: samples.buffer`）——4 字节/采样，比 int16 大一倍
- 判定结果 `isSpeech` 要从 host 经 JSON 回到客户端才能计数（`client.tsx:1386-1390`）

**代价（可量化）**：
- 确认延迟 = 轮询量化（平均 64ms）+ 上行 RTT + host VAD 推理 + `confirmFrames × 128ms`。**栅格是 128ms 不是 100ms**（64ms 帧 + `>=100ms` 阈值 ⇒ 攒两帧；见 S7 与 `bench-echo-gate.mjs` §4），默认档确认窗 384ms。CONTEXT 记录的实测 ≈525ms 与该模型吻合
- 复杂度不可约：为了在无序传输上维持顺序语义，系统里现在有 **5 套代际计数器**——`segmentEpoch`（asr.ts:185）、`detectGeneration`（asr.ts:197）、`resetGen`（asr-host.ts）、`turnGen`（index.ts:485）、TTS `q.epoch`（tts-queue.ts）。每一套都对应过一个真实竞态 bug

**判断**：这些代际计数器不是过度设计，它们是**传输选型的必然产物**。换成单会话 WebSocket（有序、有状态、双向），其中至少 3 套可以塌缩成一个 stream 级 seq。

> 建议见 [ADR-0003](adr/0003-realtime-transport.md)（提议）。

#### A2 `client.tsx` 是 2307 行的 god-file

一个文件里同时装着：SSE bus、Web Audio 播放引擎、AEC 参考池、NLMS 调度、手势与快捷键、状态条 UI、打断状态机、telemetry 视图。改任何一块都要在 2300 行里定位，评审成本高、回归面大。

建议拆分边界（按依赖方向，非按行数）：`voice-bus.ts`（SSE/状态）｜`audio-engine.ts`（播放 + 参考回传）｜`echo-ref.ts`（参考池 + delay 估计）｜`interrupt.ts`（打断状态机）｜`client.tsx`（只剩 UI 与手势）。

#### A3 构建产物入库 + 人工「同步」

`lib/client.js`（3853 行）、`lib/index.js`（2522 行）随源码一起提交，靠 `chore: 同步 lib/client.js 构建产物` 这类提交手工对齐——git log 里至少 5 次。**任何一次忘了同步，用户装到的就是旧行为**，而这在语音这种"改一个常数就换一种体感"的项目里极易发生。

修法（二选一）：① `.gitignore` 掉 `lib/`，`prepack` 已经会构建，npm 发布不受影响；② 保留入库但在 CI 加一步 `npm run build && git diff --exit-code lib/`，产物漂移直接红。

#### A4 CI 的覆盖缺口是真实的

- `ci.yml:20-23` 明确不跑 `typecheck`（理由充分：宿主类型包未发布到 npm）。但结果是**host 侧类型回归只能靠本机**，换人/换机即失守
- **6 个测试文件不在 `npm test` 里**：`integration-fork.mjs`、`wakeword.test.mjs`、`verify-bazong-path.mjs`、`verify-kokoro.mjs`、`verify-preview-loop.mjs`、`verify-speaker-gender.mjs`。其中 `wakeword.test.mjs` 对应的是最近才复活的唤醒词功能——**有测试，但永远不跑**
- 根目录 `test/` 下 16 个临时探针脚本（`debug-toggle2.js`、`probe2.js`、`probe-page.js`…）入库，与真正的用例混在一起

#### A5 单活会话是模块级全局状态

`client.tsx:23-28` 的 `isSpeechTrueCount` / `interruptFirstAt` / `isSpeechFalseRun` 是**模块级变量**，注释里也承认"全局单活架构下"成立。当前无碍，但它把"一个宿主同时服务多个语音会话/多用户"这条演进路径焊死了。是否需要这条路，属于战略问题（见 §6 Q5）。

### 2.2 声学算法视角

#### S1【最高杠杆】VAD 跑在 host，判定必须过网

打断的判定信号（Silero `isDetected()`）在 host 产生（`asr-host.ts:643`），客户端只是计数器。这意味着**每一次判定都要付一次网络往返 + 一次轮询量化**。

Silero VAD 是 ~2MB 的 ONNX，实时因子在浏览器 WASM 下远小于 1，完全可以跑在采集侧的 AudioWorklet/Worker 里。下沉后：

| 指标 | 现状 | 下沉后（估算） |
|---|---|---|
| 确认延迟 | ~525ms（实测；其中 384ms 是确认窗） | ~150–250ms（纯 `confirmFrames × 32ms 帧` + 本地判定） |
| detect 通道上行 | 播放期恒定 ~64 KB/s | 归零 |
| 判定与音频帧对齐 | 有 128ms 量化误差 | 帧对齐，无量化 |
| 失败模式 | 网络抖动 = 打断失效 | 与网络解耦 |

**这是全篇 ROI 最高的一条。** 详见 [ADR-0002](adr/0002-client-side-vad.md)（提议）。

#### S2 分段门限是固定常数，口径与回声地板不一致

`asr.ts:107` `SPEECH_RMS = 0.015` 是**硬编码固定阈值**，用于判断"是否开始一段语音"。而回声地板 `echoFloorRms` 是自适应的（`asr.ts:580-590`）。同一个系统里，两个同类判定一个自适应一个不自适应。

后果：风扇/空调/咖啡厅底噪超过 0.015 时，`speechActive` 常真 → 持续建段 → 每 100ms 发一次 partial → host 流被噪声喂满 → 靠 `MIN_SPEECH_MS`(250ms) 和端点 VAD 兜底才不误发。**能用，但是在浪费算力和带宽兜一个本可以在源头解决的问题。**

修法：复用已有的滚动地板思路，把开段门限改成 `noiseFloor × 门限比`，与 `echoFloorRms` 同一套代码。

#### S3 AEC 与 delay 估计跑在主线程

`audio-worklet.ts` 只做重采样，NLMS 与互相关都在主线程的 `handleAudio` 里（`asr.ts:548` → `client.tsx:686-724`）。

具体开销：
- NLMS 1024 taps @16k：滤波 + 权重更新 ≈ **33M 次乘加/秒**，纯 JS，主线程
- delay 估计：`client.tsx:690-691` **逐采样 `push` 进普通 `number[]`**（16000 次/秒的 boxed number push），再每 2s 做一次 `Float32Array.from()` + `splice(0, drop)`

这条路径只在原生 AEC 失效时才走——**而那恰恰是最需要稳的兜底场景**（耳机 / Safari）。主线程被 React 渲染占住时，AEC 帧处理会抖，而 AEC 对时序抖动敏感。

修法：把 `NlmsAec` + `estimateBulkDelay` 整体搬进 AudioWorklet（两者都是纯模块，无 Web Audio 依赖，`aec.ts` 顶部注释也写了"可单测"——迁移成本低）。

#### S4 自研 AEC 的兜底路径仍未根治，应该做第二次减法

ADR-0001 已诚实记录：`delay=0` 错位问题未解，需 FDLMS+RES。现状是**这条路径存在但不可信**。

两条路，建议选后者：
- (a) 补 FDLMS + 残差抑制 —— 工作量大、验证难（没有基准，见 S6），且收益只覆盖少数场景
- (b) **把自研 AEC 从"消除"降级为"探测"**：用它算 ERLE，ERLE 低于阈值就判定"本设备不具备自动打断条件"，UI 直接建议/自动切 `manual`。这是 ADR-0001 那次减法的自然延续——承认物理边界，把不可靠的自动行为换成 100% 可靠的显式手势

#### S5 缺一条几乎免费的二线防御：文本级回声否决

打断触发后，系统没有校验"刚才被判为用户语音的那段，内容是不是正在朗读的句子"。而 TTS 正在朗读的文本是**已知的**（`tts-queue.ts` final 帧带 `text`）。

廉价实现：打断后本段定稿文本与"打断时刻正在朗读的句子"做字符级重合度比对，重合度高 → 判定为回声误打断 → 记一次 telemetry（第一步只观测不动作，攒够数据再决定是否自动恢复朗读）。

这条的价值不只在纠错，更在于**它把"误打断率"从主观体感变成可统计的数字**。

#### S6【最大过程风险】所有声学参数是手调常数，无回归基准

清点一遍散落的魔数：

| 常数 | 值 | 位置 |
|---|---|---|
| `echoGateDb` | 6 dB | 设置项默认 |
| 检测 VAD 阈值 | 0.35 | `asr-host.ts:330` |
| 端点 VAD 阈值 | 0.5 | `asr-host.ts:294` |
| `confirmFrames` | 3/2/1 | `client.tsx:32` |
| `peakDecay` 基数 | 0.9 / 64ms | `asr.ts:578` |
| `floorAlpha` 基数 | 0.98 / 64ms | `asr.ts:579` |
| `SPEECH_RMS` | 0.015 | `asr.ts:107` |
| `VAD_CONTINUE_RMS` | 0.02 | `asr-host.ts:149` |
| `MIN_SPEECH_MS` | 250 | `asr.ts:112` |
| 确认窗口 | 800/350/400ms | `asr-host.ts:151-154` |
| delay 置信门 | peak > 0.5 | `client.tsx:708` |
| 迟滞 | 连续 2 拍假才减 1 | `client.tsx:1426-1428` |

这 12 个数每一个都是真机试出来的，而**它们的正确性没有任何一行代码保护**。ADR-0001 的诊断证据（"resid 从 0.11 降到 0.0017~0.0255"）是一次性的、口头的，没有变成 fixture。

`test/aec.test.mjs` 测的是 NLMS 的数值行为，不是端到端的门控决策。也就是说：**今天任何人改动 `peakDecay` 或 VAD 阈值，CI 全绿，自打断可能已经回来了。**

这是全篇最需要立刻投资的一条。详见 [ADR-0004](adr/0004-acoustic-regression-harness.md)（**已接受**）。

#### S7【2026-09-02 真机判定】门控从未被查询到；棘轮机制存在但未发作

建基准当天先在合成信号上得到"门控判别力≈0"，**随后被真机 fixture 推翻**。最终结论：

| | 合成预测 | 真机实测（①纯听 / ②打断） |
|---|---|---|
| 纯回声期门开率 | 99.8% | **0.3% / 27.1%** |
| 地板冻结率 | 85–97% | **0.3% / 16.4%** |
| 地板低估回声 | 28–57 dB | **0.1 / 2.8 dB** |

**真正的结论来自一列合成信号给不出的数据**：朗读期 Silero **0/777 帧**把回声判成语音。
打断需要先连续判真才会查询门控 ⇒ **门控这段代码从未执行过**。拦住自打断的是 VAD 与
ADR-0001 的原生 AEC 决策，不是这道门。`echoGateDb` 无效——因为"没走到"，不是"判错了"。

棘轮机制本身（`asr.ts:588`/`:591`）是代码的直接推论，真实存在，且 ①→② 之间冻结率翻了
50 倍；但它是轨迹依赖的双稳态，**没有任何分布统计量能预测它**（crest / 中位均值 / p90中位 /
调制周期全试过，都不单调）。原生 AEC 失效那一格仍无数据，是留下的风险。

完整记录与方法论教训见 [findings/2026-09-02-echo-gate-ratchet.md](findings/2026-09-02-echo-gate-ratchet.md)。

#### S8【2026-09-02 真机实测】打断确认被在途往返拖长：951ms vs 理论 384ms

检测通道被 `detectInFlight` 串行化，下一拍必须等上一次 HTTP 往返。稳态 p50=128ms 很好，
但②录制里 p99=449ms、max=758ms，**且停顿恰好落在打断时刻**，把三帧确认拉到 951ms。
这让 ADR-0002（VAD 下沉）从"优化"变成"修尾部 bug"。见
[findings/2026-09-02-barge-in-latency-stall.md](findings/2026-09-02-barge-in-latency-stall.md)。

### 2.3 AI 应用工程师视角

#### I1 端点判定的语义层是 20 个词的正则

`asr-host.ts:158` 的 `CONJUNCTION_TAIL` 用正则匹配「然后/还有/以及/…」来决定多等 800ms。这是一个诚实的启发式，但它的覆盖是随机的：中文口语里"呃…"「就是说」「我想想」「那个」这些真正高频的犹豫标记不在表里，而它们才是 700ms 静音断句最容易切碎的地方。

演进方向（按成本递增）：
1. 把词表变成可配置 + 加入犹豫词/填充词（1 小时，立刻有收益）
2. 用韵律特征（末音节基频下降 / 能量衰减斜率）做二值判据——不需要模型，DSP 即可
3. 上专门的 turn-detection 小模型（业界已有开源方案），把「说完了没」从静音时长问题变成语义问题

#### I2 首音延迟 = 整句合成时间（协议已支持流式，实现没用）

`tts-queue.ts:298` `await this.engine.synthesize(item.text)` 是**整句合成完才发第一帧**；`:304-312` 明确注释"单 chunk（整句音频）+ final 帧"。而帧协议里 `chunkId` 字段（`tts-queue.ts:75`）本来就是为分块设计的。

后果：一句 30 字的回复，用户要等完整一句合成完才听到第一个音。Edge 的 `toStream()` 本身是流式的（`tts-queue.ts:130` 用 `for await` 把它收干了）。

两级改法：
- 低成本：首句在逗号处切短（只对每轮第一句生效），首音时间立降
- 正解：把 Edge 的 `audioStream` 逐块下发（`chunkId` 递增），客户端用 MSE 或分块解码起播

另外，本地引擎（Kokoro CPU int8）的 RTF 在长回复下可能 >1，队列会持续落后——这条要么用「本地引擎自动降低并发/缩短句长」缓解，要么在文档里明确不承诺。

#### I3 级联架构的天花板，需要现在就决定是否留门

现在是 ASR → 文本 → LLM → 文本 → TTS 的经典级联。它做不到：保留说话人语气、边听边想（overlap）、真正的重叠对话、以及非语言信号（笑、叹气）。

**不建议现在就转 speech-to-speech**（成本、模型可得性、本地推理算力都不支持）。但建议现在就明确回答："我们的接口是否为它留门？" 具体是：TTS/ASR 是否抽象在一个可替换的 `VoicePipeline` 接口之后，而不是像现在这样，打断逻辑直接耦合到"句子"这个级联架构特有的概念上。

#### I4 中英不对称，README 未披露

- 流式模型：`sherpa-onnx-streaming-zipformer-**zh**-int8`（`asr-host.ts:53`）——纯中文
- 定稿模型：SenseVoice `zh-en-ja-ko-yue`（`asr-host.ts:68`）——多语种

后果：说英文时**实时字幕基本不可用，但定稿是对的**。这是一种会让人以为"坏了"的体验。README 只说"识别为简体中文优先"，没说清这条不对称。

#### I5「隐私优先」叙事与默认引擎存在张力

README 的卖点是「零 API Key · 识别本地」，而默认 TTS 引擎是 Edge 云端——**用户的每一句 AI 回复文本都会发给微软**。README 确实写了，但写在功能表里，不在卖点旁边。

另外 `msedge-tts` 是对微软非公开接口的封装，不是有 SLA 的 API。**默认路径踩在一个第三方随时可以关掉的面上**，需要：① 卖点措辞明确区分"识别本地/朗读云端"；② 准备被封时的降级路径（自动回落本地引擎 + 状态条提示）。

#### I6 有埋点，无聚合

`client.tsx` 的 telemetry 链很完整（utterance-end → endpoint-fired → submitted → first-llm-token → first-sentence-text → first-tts-chunk → first-audio-played，加 `interruptConfirmMs`），但**只打 console，需要 localStorage 开关**。没有 P50/P95，没有跨会话汇总。

结果就是：所有性能判断都是"我试了一下感觉…"。埋点已经付过成本了，聚合是几十行的事。

## 3. 红线（不要试图突破的边界）

1. **残差回声 ≥ 用户语音时，信号级方法不可分**（ADR-0001 已记）。外放 + 无原生 AEC 的场景，`auto` 打断不应做任何承诺，`manual` 是正解而不是降级。
2. **自然停顿的物理下限**：人类句内停顿常态 300–800ms。把静音断句压到 300ms 以下必然切碎句子——这不是调参能解决的，只能靠语义/韵律层（I1）。
3. **本地 TTS 的 RTF 受 CPU 限制**：长回复下队列落后是必然，不要在文档里承诺"本地引擎也实时"。
4. **浏览器原生 AEC 是黑盒**：`getSettings().echoCancellation === true` 只说明约束被接受，不说明效果。要判效果只能测 ERLE（S4）。

## 6. 五个战略问题（Q1 / Q4 已于 2026-08-30 拍板）

**Q1｜第一用户是谁：外放的桌面用户，还是戴耳机的开发者？**
✅ **已定：都是第一用户。**

这条回答否掉了"默认按耳机场景调、外放的人自己改设置"这个省事方案。直接后果：
- `bargeInMode` 增加 `detect` 取值并成为新默认，系统自己探测本机声学条件决定 auto / manual
- `echoGateDb` 降级为高级选项，README 排障表不再教用户调分贝
- 硬约束：降级必须发生在**第一次自打断之前**，否则对外放用户等于没做

→ 详见 [ADR-0005](adr/0005-barge-in-auto-degrade.md)（已接受）。第一级探测（`echoCancellation === false` → 落 `manual`）零依赖可立即做；第二级（ERLE 阈值降级）等 ADR-0004 标定。

**Q2｜「隐私优先」是承诺还是特性之一？**
如果是承诺，默认引擎不应是 Edge 云端。建议：卖点措辞改为「识别全本地 · 朗读可选本地」，并补 Edge 不可用时的自动降级。

**Q3｜中文单一语种是长期定位吗？**
如果是，把它写进 README 顶部当作定位而不是限制；如果不是，流式模型需要换成双语，这会改变模型体积预算（当前 zh 160MB + SenseVoice 228MB）。

**Q4｜愿意为回归基准付一次性成本吗？**（录制真机 fixture + 写评测脚本）
✅ **已定：做。** [ADR-0004](adr/0004-acoustic-regression-harness.md) 转「已接受」。

落地时发现一个可以大幅降低门槛的分层（`test/aec.test.mjs` 已有先例：确定性合成信号、无需麦克风）：
- **第一批不需要任何录音**——用确定性合成 fixture 先把「判定链纯函数化 → 重放 → 指标 → 报告」整条管线跑通并进 CI，守住逻辑回归
- **第二批才需要录音**——真机 fixture 补上合成信号抓不到的真实声学（扬声器非线性、原生 AEC 的 RES 残留、蓝牙延迟抖动）

这样"2–3 天"里绝大部分不阻塞在录音上，用户的录制动作可以往后排。

**Q5｜要不要为 speech-to-speech 留架构门？**
建议：留门但不实现——把 ASR/TTS 收进一个 `VoicePipeline` 接口，打断逻辑不再直接依赖"句子"概念。成本约 1 天，换掉未来的一次大重构。
