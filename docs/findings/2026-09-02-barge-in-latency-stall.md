# 发现：用户一开口，检测通道就把自己关小了

- 日期：2026-09-02（**当日经第三次真机录制定位到根因，前两版归因均被推翻**）
- 状态：**根因已确认并修复**
- 证据：三条真机录制；决定性数据来自 A 档新增的 `detects` 往返埋点

---

## 一句话

`handleAudio` 里「播放中且 rms 超门限」的帧走了一条带 `return` 的分支，而**这个 `return`
把函数末尾的轮询块一起跳过了**。于是：**用户说得越响、越连续，打断检测通道发得越少**——
请求只在音节间隙漏出去一次。实测打断窗口内本应发 47 次，实际只发 10 次。

---

## 归因过程（两次错误，值得记）

| 版本 | 归因 | 被什么推翻 |
|---|---|---|
| 初版 | 宿主忙（TTS 合成 / LLM 流 / ASR 解码共用 Node 事件循环），HTTP 往返被拖长 | 埋点实测**往返 p50=6ms，p99=20ms，max=60ms** ——宿主根本不忙 |
| 二版 | 轮询 tick 被在途请求吞掉，量化到 128ms 倍数 | 修掉之后段内间隔 p99 从 449ms 降到 141ms（**这一条是对的，但不是主因**），打断窗口仍有 255/523/576ms 停顿 |
| **三版（确认）** | **人声帧跳过整个轮询块** | 逐帧核对：每个 `rms>0.015` 的帧都没有发请求，只有掉回门限以下的帧发了 |

**两次都是在没有埋点的情况下靠推理归因，两次都错。** 决定性证据是 `detects` 里那一列
往返耗时——它一到手，"宿主忙"的假设立刻不成立，剩下的时间只能花在客户端，范围一下就
缩到了 `handleAudio` 内部。

---

**零例外**：超过 `SPEECH_RMS = 0.015` 的帧一律没发请求。

打断窗口（64.5–70.5s）播放期共 35 帧，其中 54% 超门限 ⇒ 实际发出 10 次，应发约 47 次。
覆盖率 **21%**（按窗口更严格口径算是 53%）。

音频帧本身节奏正常（帧间隔 max 66–74ms），往返 5–15ms。**时间全花在"根本没发请求"上。**

## 代码

```js
} else if (rms > SPEECH_RMS) {
  if (config.isPlaying?.()) {
    if (speechActive) finalizeSegment(true)
    return              // ← 这里
  }
  ...
}
// ……函数末尾……
const nowMs = Date.now()
if (nowMs - lastPollAt >= PARTIAL_INTERVAL_MS) {   // ← 被上面的 return 跳过
  if (playingNow && !speechActive && !holdActive) void requestDetect()
```

讽刺的是，这个分支上方的注释写着：

> 释放 speechActive 后本帧起检测通道接管打断，**防「陈旧 speechActive 饿死检测通道」**

——而紧跟着的 `return` 干的正是"饿死检测通道"。注释描述的意图是对的，实现少考虑了一步。

音频**是**被缓冲的（`detectChunks.push` 在分支链之前），所以数据没丢，只是发不出去：
埋点里 `n`（单次上行样本数）从 2048 一路涨到 9216，正是积压的证据。

---

## 修复

把 `return` 改成 `else`——本帧仍然不入段（自聊防护语义不变），但轮询块照常执行。

```js
if (config.isPlaying?.()) {
  if (speechActive) finalizeSegment(true)
  // 不 return
} else {
  ...原分段逻辑...
}
```

改动 6 行，不动任何判定算式。

**回归守卫**（两道）：
1. `test/verify-client.mjs` 断言产物里该分支后面是 `} else {` 而不是 `return`
   （esbuild 会剥注释，所以断言代码形状而非注释）
2. `scripts/analyze-fixture.mjs` 新增**检测通道覆盖率**指标：播放期应发 N 次、实发多少，
   并单独算打断窗口的覆盖率，低于 80% 直接告警。用修复前的录制验证过——它确实报警了

---

## 修复效果（**已实测确认**，第四条录制 `build=120f2c5`，三次真实打断）

| 指标 | 修复前 | 修复后 | 理论下限 |
|---|---|---|---|
| 打断窗口覆盖率 | 56% | **100%**（24/24，三段说话逐段算） | 100% |
| 段内回报间隔 p99 | 449ms | **143ms** | 128ms |
| 段内回报间隔 max | 758ms | **217ms** | — |
| `confirmMs` | 753 / 951ms | **252 / 268 / 272ms** | 256ms |
| **端到端（张嘴→停播）** | **1355ms** | **533 / 597 / 199ms** | — |

`confirmMs` 三次都贴着理论下限（256ms），说明检测通道既没被跳过也没被拖延。

端到端的波动（199~597ms）来自「开口时刻落在 128ms 栅格的哪个相位」——最好的一次
（199ms）几乎是即时，最差的一次（597ms）也已经比修复前快了一倍多。

> **顺带更正一个我算错的常数**：`confirmMs` 的理论下限是 **2 × 128 = 256ms**，不是我
> 此前反复写的 384ms。3 帧确认之间只有 2 个间隔。384ms 是「从开口到第三帧」的量级，
> 不是 `confirmMs` 这个指标的口径。ADR-0003 与 review 里的相关数字按此理解。

### 分析脚本同时修掉的两个统计错误

1. **回报间隔跨越了非播放期**：初版把两轮对话之间 9.5s 的静默当成"停顿"。改为只在
   连续播放段内部统计。
2. **打断窗口覆盖率的分母取了首末帧**：三段说话时，段与段之间的空隙也被算进分母，
   覆盖率虚低到 62%。改为逐段计算，实际是 100%。

两个错误都会让人误判"还有问题"，属于**指标本身的 bug**——已用修复前的录制回归验证：
改正后的脚本在旧录制上仍然报警（56% / 753ms），在新录制上全绿。

## 与 ADR-0003（VAD 下沉）的关系

这条**削弱**了 ADR-0003 的紧迫性，不是加强：

- 原本以为尾部退化来自宿主事件循环争用 → 只有下沉能解
- 实测往返 6ms，宿主一点不忙 → **纯客户端逻辑 bug，6 行就修好了**

修完之后，剩下的延迟是 384ms 确认窗（3 × 128ms 栅格）+ Silero 窗口。
ADR-0003 能把它压到 ~150–200ms，但那是**从 500ms 到 200ms 的优化**，
不再是"修一个会在最需要时崩掉的尾部"。

ADR-0003 里那段「本 ADR 分量因此上调」的话要撤回。

## 教训

1. **两次归因，两次错，都是因为在没有埋点的情况下推理。** 第一版怪宿主、第二版怪节拍
   量化，都是"听起来合理"的解释。真正的答案（一个 `return`）没有任何间接证据能指向它。
2. **埋点应该记"有没有发生"，不只记"发生得多快"。** 我最初只记了回报间隔，那只能看出
   "慢"；加上"每次请求的往返耗时"之后，才能做减法定位到"时间不在网络上"。
   再加上"覆盖率"（应发 vs 实发），这类 bug 才会自己跳出来。
3. **注释写了正确意图不等于代码实现了它。** 这段代码的注释明确说要防止饿死检测通道，
   紧邻的一行却造成了它。评审时读注释容易被带着走，得读控制流。
