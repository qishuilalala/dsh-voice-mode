# 发现：打断确认被在途 HTTP 往返拖长，实测 951ms（理论 384ms）

- 日期：2026-09-02
- 状态：**真机实测**（`build=04b5973`，外放，原生 AEC 生效）
- 复现：`node scripts/analyze-fixture.mjs <fixture> ` §3

---

## 一句话

检测通道被 `detectInFlight` 串行化：**下一拍必须等上一次 HTTP 往返回来**。稳态下这没问题
（p50=128ms），但宿主一忙，单拍就被拖到 449–758ms——而它**恰好发生在打断时刻**，
把默认档的三帧确认从 384ms 拉到 **951ms**。

---

## 实测

真机录制 ②（打断场景）里唯一一次真实打断：

```
用户开口（标注）      33.30s
残差跳到 0.0775       34.31s   ← 这一拍没有 VAD 回报（请求在途）
VAD 首次判真          34.38s   T
第二次判真            34.57s   T      间隔 190ms
第三次判真            35.33s   T      间隔 758ms  ← 停顿
hardBreak 触发        35.35s          confirmMs = 951
```

回报间隔分布（播放期 278 次）：

| 分位 | p50 | p90 | p95 | p99 | max |
|---|---|---|---|---|---|
| 间隔 | 128ms | 130ms | 132ms | **449ms** | **758ms** |

| confirmFrames | 理论 | 实测 p50 | 实测 p90 | 实测 p99 |
|---|---|---|---|---|
| 3（默认） | 384ms | 384ms | 388ms | **1015ms** |
| 2 | 256ms | 256ms | 259ms | 645ms |
| 1 | 128ms | 128ms | 130ms | 449ms |

对照录制 ①（纯听，全程无人说话，504 次回报）：**p99=132ms，max=166ms，一次停顿都没有。**

---

## 机制

两层叠加：

**第一层 · 名义栅格是 128ms 不是 100ms**（已确认，纯算术）
AudioWorklet 每 1024 样本 = 64ms 投一帧（`audio-worklet.ts`），`asr.ts:700` 的派发条件是
`nowMs - lastPollAt >= 100` 且仅在派发时推进 `lastPollAt` ⇒ 64ms 的帧必须攒两帧才够 100ms。
三档确认窗实际是 **384 / 256 / 128ms**，不是注释里写的 300/200/100ms。
真机 p50 = 128 / 384ms，与此完全吻合。

**第二层 · 串行化把栅格变成 RTT 的函数**（本条新发现）
`requestDetect()` 开头 `if (detectInFlight) return`（`asr.ts:352`），响应回来才清标志。
所以真实节拍是 `max(128ms, 上一次往返耗时)`。往返耗时包含：

- 上行 f32 PCM（每拍约 8KB）
- 宿主 `/asr?vadOnly=1` 处理：Silero 推理
- **与 TTS 合成、LLM 流式、ASR 解码共用同一条 Node 事件循环**

朗读期这三件事都在跑。事件循环被占住，`/asr` 的响应就排在后面。

---

## 为什么停顿偏偏发生在打断时刻

这不是巧合，有两个方向的解释，**目前无法从现有数据里区分**：

1. **宿主侧**：用户开口 → 检测 VAD 从"静音"转入"语音段"，sherpa 内部开始分配/累积段
   （`asr-host.ts:643-646` 的 `isDetected()` + 排空循环），这一拍的推理与内存工作量高于静音拍。
2. **客户端侧**：同一时刻主线程也在忙——`handleAudio` 里跑着 NLMS 调度、录制器在写 Int16 轨，
   React 在更新状态条。主线程一卡，`fetch` 的发起与回调都会延后。

录制 ① 全程无停顿这一点，更支持解释 1（① 里宿主同样在做 TTS 合成，但检测 VAD 始终在静音态）。
**但这仍是推断，不是结论。** 区分方法：在 `requestDetect` 两端各打一个时间戳（发起、响应到达），
分离"请求在途"与"主线程没排上"两种停顿。这是下一步该加的埋点。

## 影响

### 对 ADR-0002（打断 VAD 下沉到客户端）
**这条数据把 ADR-0002 从"优化"升级为"修 bug"。** 原本的论证是"省掉 128ms 量化 + 往返"，
现在还要加上：**串行化 + 事件循环争用会让确认窗在最需要的时刻退化 2.5 倍**，而且这是尾部
风险，平均值完全看不出来（p50 完美，p99 崩）。

VAD 跑在采集侧后，判定与网络、与宿主事件循环全部解耦，栅格恒等于音频帧率。
ADR-0002 的收益估算应据此上修。

### 对 `interruptLevel`
降档（2 = 1 帧确认）能把 p50 压到 128ms，但 p99 仍有 449ms，且失去多帧确认对 VAD 抖动的
抑制。**在 ADR-0002 落地前，降档不是好的换取方式。**

### 对文档
`client.tsx:1358-1359` 的注释"墙钟节拍 100ms/拍，三档确认约 0.3/0.2/0.1s"两处都错，
应改为"128ms/拍，三档确认 384/256/128ms（宿主繁忙时可退化至 1s 量级）"。

---

## 顺带：一个可以立刻做的缓解

`requestDetect` 现在是「串行 + 到点才发」。改成**允许一个在途请求的同时预备下一包**
（或把上行改成 int16 减半体积），可在不动架构的前提下压低尾部。属于 ADR-0002 落地前的临时缓解，
**但要先加上面说的两端时间戳埋点确认瓶颈在哪一侧**，否则可能优化错地方。
